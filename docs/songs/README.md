## 공통 규칙

### 디렉토리

```
<곡>/
  *.py          빌드·계측·렌더 도구        ← 추적
  *.md          기획·문서                 ← 추적
  out/          빌드 산출물               ← .gitignore (빌드하면 다시 생긴다)
  release/      현재 리비전 납품물         ← 추적 (단, MP3 는 제외)
```

**`out/` 을 추적하지 않는 이유.** 빌드가 결정적이라(같은 소스 → 바이트 동일한 MIDI)
커밋할 이유가 없다. 리비전마다 MP3 를 커밋하다 `.git` 이 **127M** 까지 불었다.
구버전 산출물이 필요하면 그 리비전을 체크아웃해 다시 빌드한다.

### 리비전

`build.py` 의 `REV` 하나만 올리면 산출물 파일명에 `_revNN` 이 박힌다.
`render.py`·`render_sf.py` 의 `REV` 도 같이 맞춘다.
무엇을 왜 고쳤는지는 **그 곡의 `REVISIONS.md`** 에 리비전마다 적는다.

### 작업 방식 — 15 리비전에서 얻은 것

1. **계측기를 만들면 꺼서 돌려 실제로 실패하는지 확인한다.** 실패하지 않는 검사는 검사가 아니다
2. **지표가 틀릴 수 있다.** "문제"로 보고된 것의 절반이 음악이 아니라 지표의 결함이었다 —
   분모를 잘못 잡음, MIDI 음높이를 오디오 스펙트럼으로 착각, 완성곡 기준을 반주에 적용
3. **한 번에 한 가지만 바꾼다.** 둘을 같이 바꿔 원인을 못 가린 적이 있다
4. **보정을 넣었으면 그 이유가 사라졌을 때 되돌린다.** 로즈를 내렸는데 기타 보정을 그대로 둬서
   8 리비전 동안 기타가 한 옥타브 높게 울렸다
5. **못 재는 것을 재려 하지 않는다.** 음원 간 음색 우열은 스펙트럼 지표로 안 갈린다 — 귀로 고른다
